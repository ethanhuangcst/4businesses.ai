HR 政策百事通和年假智能体需求

# HR Assistant 本地专家 当前工作区的 `hr-assistant-agent/` 存放模拟数据和种子包。本地专家包单独放在 WorkBuddy 专家注册目录，注册为单角色专家「HR 助理」，分类为「运营人力」。桌面端和微信端统一使用 `<已绑定工作区>/hr-assistant-agent/data/`，不在专家安装目录中保存请假记录。未绑定工作区时，助理先请用户指定工作区，不猜路径或新建第二份台账。 ## `hr-assistant-agent` 的目标 这是一个智能体概念验证（POC），使用模拟数据，实现下面三类功能： 1. 员工政策百事通问答助理。 2. 查看剩余的假期。 3. 提交请假申请（POC 自动审批）。 ## Input ### 已绑定工作区的 `hr-assistant-agent/data/` 包含两个文件 1. `data/employees-db.json` 2. `data/company-policy.md` ### 专家构建完成后，将初始文件打包为 `hr-assistant-agent-seeds.zip` 1. 只制作一份种子包，包含上述两个初始文件，不包含脚本或运行后新增的请假记录。本地验收和跨机器分享使用同一个种子包。跨机器分享前确认云端地址和下载权限，再上传该种子包。 2. 收件人安装专家后，在自己的 WorkBuddy 工作区手动说「初始化」。专家将种子文件安装到该工作区的 `hr-assistant-agent/data/`。再次初始化只补缺失文件，不覆盖已有数据。找不到种子包时，助理请用户提供该种子包，不现场生成数据。 3. 初始化和年假台账脚本随专家包交付。初始化脚本校验种子包后安装数据，不执行种子包中的内容。台账脚本负责日期计算、校验和写入。用于生成模拟数据或重建种子包的脚本只放在构建目录，不随种子包交付。 ## Requirement ### 使用入口 1. 用户可以通过 WorkBuddy 直接召唤专家，在对话中使用。 2. 用户也可以用 WorkBuddy 助理绑定微信后，在微信对话中直接召唤专家。微信直接召唤是首版验收的硬条件。先验证微信能直接召唤本专家并读取指定工作区的模拟数据，再验证微信和桌面端能查询、提交并看到同一份台账中的更新。只能续聊桌面端已启动的会话不算通过。 ### 功能 #### 公司政策百事通 ##### 问答助理 用户输入问题后，助理从已绑定工作区的 `hr-assistant-agent/data/company-policy.md` 查找答案，在对话中回答并引用政策编号和条款。缺少影响结论的信息时，先追问。 ##### 公司政策：以现有文件为基础扩充 来源：[mock-hr-policies.md](../../sample-agents/hr-assistant/mock-data/mock-hr-policies.md)。 1. 增加上海、北京、成都、新加坡、东京和伦敦的模拟差旅标准。写清航班舱位条件、住宿每晚限额、餐补每日标准、币种和未列城市的处理方式。短期差旅与跨城搬迁标准分开。 2. 扩充试用期、报销、证明开具等常见问答，每条答案对应手册条款。 3. 手册可读取但找不到答案时，回复：“员工手册中目前没有相关的规定，请咨询 HR。” 手册缺失或读取失败时，说明数据不可用。 #### 查询个人假期 ##### 数据源 `data/employees-db.json` 预设 20 位虚构员工，假期只涵盖年假。模拟数据依据 `data/company-policy.md` 制作，覆盖无请假记录、零余额、年中入职、离职后复聘和已有未来请假等场景。手册不再预设默认员工或固定个人余额，个人年假信息以台账为准。 ##### 员工选择 用户提出假期查询后，助理先提示：「这是 HR 助理 POC，不做真实的身份验证，请说明要查询哪一位员工的年假信息。」然后按数字序号列出 20 位员工，接受序号或姓名。 ##### 请假详细数据 1. 列出该员工在 2026 年演示周期享有的年假总天数。查询和请假统一以北京时间 `2026-11-22` 为演示日期，不按电脑当天判断，首版不自动跨年。助理将此日期标明为模拟日期。 2. 逐笔列出请假记录，包括提交时间、事由、休假起始日期、结束日期和天数。 3. 列出剩余年假天数。年度额度、请假记录和余额须能核对。 法定年假使用预设的模拟核定值，企业补充年假按手册计算。模拟核定值不代表真实法定标准。 #### 请假 ##### 员工选择 用户提出请假后，助理先提示：「这是 HR 助理 POC，不做真实的身份验证，请说明要以哪位员工的身份请假。」然后按数字序号列出 20 位员工，接受序号或姓名。 ##### 提交请假 1. 先展示该员工的请假详细数据，格式与「查询个人假期」相同。 2. 依次询问三个问题：请问您请假的起始日期？请几天？事由？事由可填「个人安排」或「不提供」，不要求私人细节。请假草稿仅在当前会话有效，用户取消或改选员工时，助理清空草稿。 3. 首版只接受晚于演示日期 `2026-11-22`、且在 2026 年内结束的整工作日申请。模拟工作日为周一至周五，不套用真实节假日和调休。起始日不是工作日、申请跨年、与已有请假重叠或余额不足时，说明原因，不写入台账。 4. 扣减时先使用较早到期的年假账户；同一天到期时，先扣法定年假。 5. 台账脚本对同一台账加写入锁，在锁内重新读取、校验和保存，防止桌面端与微信端同时提交时互相覆盖。同一员工、同一起始日和天数的申请重复提交时，返回原申请编号，不再扣减。新申请校验通过后直接写入，无需二次确认。 6. 写入成功后回复「模拟审批通过」，并列出申请编号、实际休假起止日期和新余额。校验或写入失败时，说明原因，不提示审批通过。 ## 智能体开工前的初始化工作 1. 以 `mock-hr-policies.md` 为基础扩充 `data/company-policy.md`，补齐差旅条款和常见问答，移除旧员工表引用及默认员工答案。 2. 构建 `data/employees-db.json`，为 20 位虚构员工准备不同场景的年假记录。 3. 将两个初始文件打包为同一份 `hr-assistant-agent-seeds.zip`。 ## 首版验收 1. 在干净的工作区手动发起「初始化」，验证两个文件可用。重复初始化只补缺失文件，不改变已有台账。 2. 在桌面端与微信端分别直接召唤专家，完成查询、请假和再次查询，验证两端使用同一份台账。 3. 验证余额不足、日期重叠的申请不会改变台账；重复提交返回原申请编号且不重复扣减。 4. 验证两端同时提交时，台账保留所有成功记录，被拒绝的申请不改变余额。

实验室设备预约专家需求

# 实验室设备预约：本地专家 ## 使用入口 `lab-mgmt-expert` 安装到个人版 WorkBuddy 的「我的专家」，显示名为「实验室设备助理」。试用版不另外登录或验证身份，预约时从人员名单里选人。 - 电脑：在 WorkBuddy 里选「实验室设备助理」。 - 微信：用自己的微信绑定个人版 WorkBuddy「助理」。能否持续调用这个本地专家，还要实测。 - 电脑和微信用同一份本地台账。本地专家和企业智能体用同一套数据结构，各自保存数据，预约不互通。 ## 数据 设备、人员、预约台账和模板随 `lab-mgmt-expert` 一起打包。电脑和微信都指向专家服务目录下同一份台账。升级时保留已有设备、人员和预约数据，不用包内初始文件覆盖。 | `lab-mgmt-expert/data/` 下的文件 | 记录的数据 | | --- | --- | | `lab-equipments.json` | 初始 50 台模拟设备。每台一条，同名设备分开记。字段有设备编号、名称、类别、用途、位置和运行状态，不设数量字段。 | | `people.json` | 初始 50 人。每人一条，记录人员编号、中文姓名、英文名（`english_name`）、部门、岗位、工号和邮箱。`lab_admin` 标记实验室管理员。测试邮箱统一用 `firstname@ethanhuang.com`，`firstname` 为小写英文名。 | | `reservations.json` | 每笔预约一条，记录预约编号、设备编号、人员编号、起止日期和时段、状态及选填用途。有变动就更新。 | | `lab-mgmt-expert/templates/` 下的文件 | 记录的数据和展示方式 | | --- | --- | | `reservation-list.md` | 预约编号、设备名称和编号、预约人和部门、起止日期和时段、状态。电脑上用表格，微信里用短列表。 | | `reservation-form.md` | 电脑上用表格，微信里用短列表。设备、预约人、起止日期和时段必填，用途选填。填过的用途写入 `reservations.json`，在预约详情里显示。 | ## 专家职责 1. **查设备空闲**：按设备名和日期查，设备名可只输一部分。未给日期时查从今天起的 7 天。匹配多台时，列出名称、编号和位置，让用户选一台再显示空闲时段。查询不创建预约。只有上一轮明确问过是否预约，用户回复“要”才进入预约流程。 2. **查预约单**：按设备名、预约人姓名、部门、岗位或预约编号查，支持模糊匹配。查到多笔时，让用户选一笔再看详情。 3. **预约**：选定设备、预约人和时段，缺什么就问什么。同名人员列出部门和工号，让用户选。只订在役设备尚未开始且没被占用的时段。维护中或停用的设备不能订。时段冲突时，列出其他空闲时段或同名设备，不自行替换。 4. **修改和取消**：优先按预约编号找，无编号时按预约人或设备查。查到多笔就让用户选。只修改或取消尚未开始且未取消的预约。修改只涉及日期和时段，沿用原编号，查冲突时排除原预约。修改校验通过就更新，即使新旧时段相同也照常更新和通知。改不了就保留原预约。取消后保留记录并释放时段。已取消的预约可查、不可改，再次取消时提示“已取消”，不发邮件。 5. **邮件通知**：新建、修改或取消成功后，通知预约人和所有实验室管理员，同一邮箱只发一封。邮件写明操作、预约编号、设备、预约人和时段。修改通知列出修改前后的时段。没有管理员时仍通知预约人，并在聊天里说明。发送失败就在聊天里说明，不补发，不撤销预约。试用版只向 `ethanhuang.com` 下的测试邮箱发送通知。 ## 规则：时段和重复提交 - 按北京时间订上午、下午或全天，不区分工作日、周末和节假日。跨日预约连续占用首尾之间的所有半天，首尾也算在内。有一个半天不能订，整笔就不保存。 - 上午从 09:00 开始，下午从 13:00 开始。用第一个半天判断预约是否已经开始。 - 用户明确要预约、修改或取消，信息齐全且符合规则就直接办，不审批，也不再问一遍。 - 电脑和微信用同一个预约工具。工具锁住台账后，按设备编号、日期和半天检查冲突，写好新文件后一次替换旧文件。 - 同一次提交重试时沿用原请求编号，返回原结果，不重复写台账或发邮件。新提交且时段没变，仍按修改办理。取消后重新预约也属于新请求。

# 关键物料缺料预警专家：本地专家 ## 使用入口 - 「关键物料缺料预警专家」是个人版 WorkBuddy 本地专家。学习者按本说明在 WorkBuddy 对话中构建自己的专家，并注册到本机「我的专家」。 - 运行目录为 `expert/`，包含脚本、种子数据、数据目录、报告目录和上传暂存目录。教学套件中，该目录由 `material-shortage-alert-seedfile.zip` 解压产生；本机专家包中，即本说明所在目录。通过个人版 WorkBuddy 对话中调用专家使用。 ## 数据来源 ### 模拟 ERP 接口 - workshop 使用公网 MCP 模拟 ERP 接口。连接器名 `erp-mock-mcp`，MCP 地址： `https://erp-mock.agent-mate.ai/mcp`。 - `get_data` 接收 `file_name`，返回当前数据空间内该文件的最新版本，包括 `file_name`、`version`、`uploaded_at` 和 `data`。 - `upload_data` 接收 `file_name` 和 `content`，按[上传校验要求](#upload_data-校验要求)校验后保存新版本。任一条件失败就返回错误，不写入新版本。 `data/` 是运行目录下的本地数据目录，保存最近一次从模拟 ERP 取回的四份文件。`data-seeds/` 是只读种子目录，仅在初始化时使用。 ### 四份源文件与数量口径 | 文件 | 内容与计算口径 | | --- | --- | | `materials.json` | 物料主数据。其他三份文件按 `material_id` 关联，单位以主数据为准。同名物料不合并。 | | `inventory.json` | 库存快照。workshop 将 `quantity` 视为 `snapshot_date` 当日结束时的可用量，不另扣占用。按料号合计同一快照日各仓库的可用量。 | | `work-orders.json` | 工单。纳入检查的工单以 `quantity` 表示 `requirement_date` 当天仍需领用的数量，不按工单原始总量计算。已完工工单不计需求。 | | `inbound.json` | 采购到货。对快照之后的确认到货，以 `quantity` 表示仍待收货的数量。`confirmed_arrival_date` 为空时不计供应，不用 `arrival_date` 代替。 | 确认到货日早于或等于 `snapshot_date` 的记录视为已反映在库存中，不再加计。`uploaded_at` 是服务端保存版本的时间，既不是库存快照日期，也不是专家导入时间。 ## 工作职责 专家承担三项工作。模拟 ERP 上传不会触发专家，不设定时任务。 ### 工作 1：初始化模拟 ERP 数据 - 用户发起检查时，专家先探测模拟 ERP：四份文件全部返回「无版本」时，提示「模拟ERP MCP 服务当前无数据，执行初始化」，随即自动初始化，不需用户再次确认。 - `get_data` 连接失败与「无数据」是两种结果：连接失败按取数失败处理，只有四份全部无版本才初始化。部分文件有版本时不初始化，按工作 2 继续。 - 初始化从 `data-seeds/` 读取四份种子 JSON，逐份通过 `upload_data` 上传。成功后提示「初始化完成，4 份种子数据传入模拟ERP MCP 服务」。任一份上传失败时停止并说明。 - 初始化不覆盖 `data/`；本地数据由工作 2 取数时更新。 ### 工作 2：取数、缺料检查与报告 #### 第一步：获取最新四份 JSON - 用户发起检查即批准自动取数。专家用 `get_data` 分别读取四份文件，成功返回的四份就是本轮最新数据，不追踪服务端更新过程，不核对上传回执或批次。 - 模拟 ERP 是经过校验的模拟数据接口，取回结果（含 `file_name`、`version`、`uploaded_at`、`data` 信封）直接覆盖 `data/` 中四个同名文件，导入时间以文件内 `uploaded_at` 为准，由报告版本表展示。 - 任一文件取数失败时，专家指出文件和原因，不覆盖本地数据，也不用旧文件补齐或继续本轮检查。 #### 第二步：批量检查缺料并生成 HTML 报告 - 正式预警只纳入「已下达」工单。「计划中」和「已完工」不计入；其他状态视为数据异常，停止本轮并指出工单。 - 检查范围为库存快照日之后至指定截止日，含截止日当天。截止日早于库存快照日时，请用户更正。快照日及以前仍待领用的已下达工单单列为「待核对」，不计入该期间的正式预警。 - 同日先计到货，再按 `requirement_date` 和 `work_order_id` 分配。旧缺口不自动结转，未知到货日期不计供应。 - 专家读取 [缺料预警 HTML 模板](reports/template/shortage-report-template.html)，将报告保存到 `reports/YYYYMMDD.html`。`YYYYMMDD` 是报告生成当天的本地日期，例如 `reports/20261121.html`。模板和输出路径均相对于本目录。 - 模板只展示已计算结果；填入的外部文本须做 HTML 转义。无需求和有需求但无缺料分别说明，两种情况都生成报告。数据有缺失时不得给出「无缺料」结论。 - 单料号查询作为追问入口。名称对应多个料号时，请用户先选料号。 #### 第三步：在对话预览并发送邮件 - 专家在 WorkBuddy 对话中提供可打开的本地 HTML 报告链接，并显示简要结果。 - 收件人使用当前 WorkBuddy 已授权的「我的邮箱」（Agent Mail 地址），不从登录账号推断。专家展示收件人和附件，经用户确认后发送简短摘要，并附上与对话预览相同的 HTML 文件。不在邮件中发送本机路径。 - 邮箱未开通、地址无法确认或邮件发送失败时，专家保留报告和对话预览，并单独说明邮件状态。 ### 工作 3：协助修改并上传数据 - 用户通过 chat 上传手动修改后的 JSON 文件，不要求 4 份全部，任何一份或多份均可。 - 专家将文件暂存到 `upload/` 目录，用脚本 `validate` 子命令校验数据和格式。 - 格式类问题（缺字段、日期格式、数量类型）由专家直接修改并说明改了什么；业务数值改动（数量、日期、状态）先列出改动项，经用户确认再改。 - 校验通过后，专家将 `upload/` 下的文件通过 `upload_data` 逐份上传。新增料号时先上传 `materials.json`，再上传引用该料号的其他文件。 - 上传成功后提示用户，并询问是否立即执行工作 2 的缺料检查，不自动触发。 ### 工作流验收 - 当前基线检查截至 2026 年 11 月 28 日。控制板 `M-1005` 的已下达工单 `WO-2026-1101` 需求为 50 块，库存为 36 块，无确认到货，报告应列出 11 月 28 日首次缺 14 块。 - 查询「密封圈」时，专家应让学员在 `M-1006` 和 `M-1007` 中选一个料号。同日多工单和数据错误使用独立测试输入，不修改基线。 - 验收时核对对话报告与邮箱收到的附件是否为同一份文件。 ## `upload_data` 校验要求 `upload_data` 按下面的规则校验。任一条件失败就返回错误，不写入新版本。记录多出的字段会原样保留。 ### 文件级 | 检查 | 通过条件 | | --- | --- | | 文件名 | 只能是 `materials.json`、`inventory.json`、`work-orders.json`、`inbound.json` | | 大小 | 不超过 2 MB | | JSON | 内容是合法 JSON | | 结构 | 顶层是对象，且含数组字段 `data` | | 记录数 | `data` 不超过 1000 条；每条是对象 | | `uploaded_at` | 可以不带。带了就必须是带时区、精确到秒的时间，例如 `2026-11-21T13:52:46+08:00`。服务保存时用服务器时间覆盖它 | ### 各文件必填字段 字符串必须是去空白后非空的字符串。日期必须是真实的 `YYYY-MM-DD`。 | 文件 | 必填字段 | 数量 | 查重键 | | --- | --- | --- | --- | | `materials.json` | `material_id`、`material_name`、`unit` | 无 | `material_id` | | `inventory.json` | `material_id`、`warehouse`、`snapshot_date` | `quantity` 为数字，且大于或等于 0 | `material_id` + `warehouse` | | `work-orders.json` | `work_order_id`、`material_id`、`material_name`、`requirement_date`、`status` | `quantity` 为数字，且大于 0 | `work_order_id` | | `inbound.json` | `record_id`、`material_id`、`material_name`、`arrival_date` | `quantity` 为数字，且大于 0 | `record_id` | `inbound.json` 的 `confirmed_arrival_date` 必填，值可以是 `YYYY-MM-DD` 或 `null`。 ### 不视为错误 - 两条记录的 `material_name` 相同。查重不用物料名称。 - 记录里带有必填字段以外的字段，例如 `spec`、`supplier`、`category`。
